# 第三阶段：6 GiB 内存约束下的全市场分钟回测设计

## 1. 目标与边界

第三阶段不是重写 V2 经济逻辑，而是把 A18 的正式 V2 事件循环改造成可恢复的
out-of-core 时间分块执行。首个真实使用目标是
`strategies/full_market_rank_descent_long` 中的 R1/R2：全市场、1 分钟、24 小时动量 Rank、
连续 Rank 递减触发、单持仓、5 倍名义以及硬止盈止损。

目标约束：

- 回测进程绝对 RSS 小于配置硬门；当前服务器建议 5632 MiB。
- 若部署在整机只有 6 GiB 的虚拟机，建议硬门降到 5120 MiB，为系统和文件缓存留空间。
- 允许用更多扫描、排序和磁盘 I/O 换取内存，不追求全年容量压测。
- 同一输入的 chunked 与 in_memory 在共同支持的场景中必须具有相同经济结果。
- 服务器宕机后从最后一个完整块继续，不能把半写入结果当作成功。
- 不修改 V1 语义，不触碰仓库中的实盘代码。

## 2. 为什么按时间分块

截面 Rank 在同一分钟必须看到当时全部有效合约。按合约切块会先得到局部 Rank，必须
额外做全市场归并，容易造成语义错误；所以核心维度固定为时间。

建议初始块为 6 小时，输入窗为：

~~~text
[core_start - 24h warmup, core_end)
~~~

按约 530 个合约估算，一个输入块约为：

~~~text
(24h + 6h) × 60 × 530 ≈ 954,000 行
~~~

列裁剪后只读取因子、成交和风控所需的时间、symbol、OHLC、合约元数据。相同输入可能
被分阶段重复扫描，以避免 bars、Rank、事件和完整产物同时常驻内存。实际块大小不是
正确性参数；若内存接近硬门，可降为 3h 或 1h，结果必须不变。

## 3. 分块数据流

每个块按以下顺序运行：

1. 扫描包含 warmup 的全市场最小列集合。
2. 在块内计算 24h 动量并执行完整截面排序。
3. 只保留 core 区间的 Rank 和策略事件，warmup 仅用于计算。
4. 从上一个检查点恢复持仓、资金、风险、Rank 序列和稳定 ID 计数器。
5. 逐时间点执行策略、风险仲裁和成交。
6. 将表按块写入 Parquet，不在 Python list 中累计整月结果。
7. 写入最小恢复状态、行数和 hash，最后原子提交该块。
8. 释放块对象后再进入下一块。

报告和全局指标在所有块完成后从 Parquet parts 流式归并，不能重新 collect 全部明细。

## 4. 内存中允许存在的内容

运行任一时刻只允许以下数据驻留：

- 当前时间块及其 24h warmup 所需的最小行情列；
- 当前分钟的全市场 score/rank 截面；
- 每合约一行左右的 Rank 递减状态；
- 当前账户持仓（目标策略最多一份）；
- 当前风险状态、冷却和下一根开盘待成交意图；
- 小型指标累加器和当前块输出缓冲。

不允许常驻：

- 整月全市场 bars；
- 整月完整 Rank 矩阵；
- 整月 positions/trades/risk Python 字典列表；
- 为报告复制一份完整 DataFrame；
- 多个时间块的 warmup 数据。

## 5. 检查点与恢复

工作区位于输出根的 `.work/v2-<identity>`。identity 同时绑定：

- run_id 和引擎版本；
- 完整配置 hash；
- dataset snapshot hash；
- 分块计划 hash、回测区间、块长和 overlap。

每块先写入 `staging/chunk-*`。状态、输出 part、行数、字节数和 SHA-256 全部完成后，
才把目录原子重命名为 `chunks/chunk-NNNNNN`。恢复时只读取连续的 committed
目录，并逐文件校验；staging 内容保留用于排错但不会被采用。

检查点包含文件引用和少量稳定计数器。状态表使用 Parquet，标量使用 JSON。它不包含
市场历史；24h 历史通过下一块 overlap 重新扫描，因此恢复内存不会随回测时长增长。

以下任一变化都拒绝续跑：配置、数据集、引擎版本、时间计划、文件 hash、行数、块编号
或边界。用户必须开始新 run，不能把不同语义的结果拼接。

## 6. 内存硬门

旧 `max_incremental_rss_mib` 只衡量相对进程启动时的增量，继续保留用于诊断。
V2 chunked 新增 `max_process_rss_mib`，衡量 worker 的绝对 RSS。每块关键阶段主动
采样；A20 还会由父进程监督独立 worker，从而处理块内瞬时峰值和强制终止。

达到硬门时必须：

1. 停止接受当前块；
2. 不生成 committed 目录；
3. 保留上一个有效检查点；
4. 报告阶段、块编号和 RSS；
5. 允许用户缩小 `chunk_interval` 后以新 identity 重跑。

## 7. 预计内存

以下是架构预算，不是实测承诺：

| 内容 | 估计峰值 |
|---|---:|
| 约 95 万行裁剪后 Polars/Arrow 数据及算子临时区 | 0.8–2.5 GiB |
| 截面排序、join、事件块输出瞬时副本 | 0.8–1.8 GiB |
| Python 引擎、状态、依赖和解释器 | 0.3–0.8 GiB |
| 安全余量 | 0.8–1.2 GiB |
| 目标进程峰值 | 2.7–5.5 GiB |

实际值取决于全市场合约数量、有效列、Polars 算法和缺失数据。A24 才以代表性真实联网
数据测量 RSS；A19 不分配大内存来模拟 OOM。

## 8. 阶段划分

- A19：配置、run identity、原子工作区、恢复校验和绝对 RSS 契约。
- A20：正式 V2 时间分块 worker，恢复 V2 状态并证明小 fixture 等价。
- A21：分块产物、流式指标和交互报告归并。
- A22：全市场 24h 动量与 Rank 递减策略状态机。
- A23：同 bar 硬止盈止损及单持仓换仓语义。
- A24：代表性真实联网全链路、报告和小于 6 GiB 的实测验收。

A24 不做全年压测。先用数天全市场或一个月的可控子区间验证真实逻辑和资源门，再由
用户决定是否执行完整一个月。
