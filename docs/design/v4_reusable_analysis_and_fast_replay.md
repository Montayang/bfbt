# 第四阶段目标：可复用分析与快速交易回放

## 1. 状态与目的

本文最初是下一版优化开发目标；用户已于 2026-08-22 明确授权实施。A27–A29 的分层
快照、稀疏回放和参数 sweep 已完成开发与离线验收，详细证据见
[`../acceptance/v4_plan.md`](../acceptance/v4_plan.md)。

当前正式全市场分钟回测会依次完成因子/Rank 分析和交易执行。即使只修改止盈止损，系统
也会重新扫描全市场、计算因子和 Rank，再执行整个持仓路径。第四阶段的目标不是跳过必要
的经济模拟，而是把不受本次参数变化影响的上游结果冻结成可审计、可复用的不可变产物，
只从最早失效的层级开始重算。

以 R4 为首个真实基准场景：

- 15 分钟 EMA7/EMA25 比值每分钟更新；
- 全市场每分钟降序 Rank；
- Rank 从至少 7 非上升到 Rank 1 产生候选信号；
- 单持仓、固定初始权益三分之一保证金、5 倍杠杆；
- 2% 止损、3.6% 止盈及当前正式成本/成交语义。

R4 只是验收样例。缓存、依赖和回放接口必须是通用能力，不能写死 EMA、Rank7、单仓或
某个策略名称。

## 2. 核心原则

1. **不会直接修改旧结果**：凡是会改变交易路径、账户状态或成本的参数，都至少重新执行
   一次确定性交易回放。
2. **按依赖失效，不按配置文件整体失效**：改变下游参数时复用仍然有效的上游产物；改变
   上游参数时只废弃其自身及全部下游。
3. **正式事实不可变**：分析快照、信号快照和正式 run 均以 manifest、内容 hash 和父级
   引用固定；成功发布后不覆盖。
4. **无前视与时点语义不变**：因子可见时间、Rank 截面、信号延迟、next-open、风险检查
   和资金费时点必须与冷启动完整回测一致。
5. **继续使用 V2 chunked**：不得通过整月全市场 `collect`、常驻完整 Rank 矩阵或复制全部
   bars 换取速度；快照生产、消费、恢复和归并都必须分块且有内存硬门。
6. **缓存不是宽松模式**：身份不完整、父产物缺失、hash 不符、字段不足或版本不兼容时
   必须 fail closed，不能静默回退到可能改变结果的近似值。
7. **研究结果与正式 run 分离**：批量参数扫描可以产生候选摘要，但只有选定配置经过正式
   回放和原子发布后，才获得正式 run ID 和报告。

## 3. 目标分层

~~~text
不可变 DatasetSnapshot
  └─ AnalysisSnapshot：因子、可交易截面、完整或有界可声明的 Rank 信息
       └─ SignalSnapshot：与账户无关的选择状态和候选交易信号
            └─ ReplayRun：账户、持仓、成交、成本、风险、指标和正式报告
~~~

### 3.1 DatasetSnapshot

继续沿用现有数据集合与正式 DatasetSnapshot。它固定市场、字段、基础粒度、时间覆盖、
分区及内容 hash，不归属于具体策略。已有月份的数据满足语义和覆盖范围时不得重复下载。

### 3.2 AnalysisSnapshot

分析快照保存后续选择阶段所需的时点化信息，至少绑定：

- DatasetSnapshot ID、manifest hash 和实际使用的区间；
- universe 配置、实现版本和逐时点有效截面语义；
- factor 名称、版本、参数、预热、缺口处理和计算频率；
- Rank 顺序、并列政策、Rank 时钟和实现版本；
- 源代码/引擎兼容版本、schema 版本、分块计划和内容 hash；
- 实际发布的 Rank 覆盖能力，例如完整截面或明确的 Top K 上限。

快照按时间分区保存，可以覆盖一个月或更长范围。子区间只有在 warmup、时点和边界语义
完整时才允许复用，不能简单裁剪掉子区间开始前所需的递推状态。

### 3.3 SignalSnapshot

信号快照消费 AnalysisSnapshot，保存与账户、仓位、止盈止损和交易成本无关的策略选择
状态及候选信号。其身份至少绑定：

- AnalysisSnapshot ID 和内容 hash；
- 选择模式及参数，例如 Rank 递减起点、入场 Rank、持平/上升政策；
- 选择时钟、调仓频率、lag、候选优先级和信号时间；
- 跨块选择状态、稳定事件 ID 和内容 hash。

R4 中把 `start_rank_at_least=7` 改成 10 时，应复用 AnalysisSnapshot、重建
SignalSnapshot；修改止盈止损时应同时复用两级快照。

### 3.4 ReplayRun

交易回放消费 SignalSnapshot 和足够的市场路径数据，重新计算：

- 初始权益、仓位大小、保证金和杠杆；
- 持仓约束、替换/加仓政策和可用资金；
- 止盈、止损、移动止损、组合退出、冷却和重新入场；
- next-open、滑点、手续费、资金费、跳空及同 bar 冲突；
- trades、positions、risk events、costs、权益、指标和报告。

ReplayRun 仍然是一次回测，不允许根据旧 trades 直接改写盈亏。退出时间改变后，后续能否
接收信号、持有什么合约、账户权益和仓位大小都可能改变，必须按时间顺序重新模拟。

## 4. 参数变化与最早重算层级

| 参数类别 | R4 示例 | 最早重算层级 | 允许复用 |
|---|---|---|---|
| 报告/发布 | 布局、run 显示名、HTML 重建 | 报告 | 全部经济产物 |
| 审计裁剪 | `audit_top_n=7` | 审计发布；若快照能力不足则分析 | 取决于 Rank 覆盖声明 |
| 风险 | 止损 2%、止盈 3.6%、冲突/跳空政策 | ReplayRun | 数据、分析、信号 |
| 资金与仓位 | 初始权益、固定保证金、权益比例、杠杆 | ReplayRun | 数据、分析、信号 |
| 成交与成本 | signal delay、fill、手续费、滑点、资金费 | ReplayRun | 数据、分析、信号 |
| 持仓政策 | 单/多仓、替换、忽略、加仓、敞口约束 | ReplayRun | 数据、分析、信号；字段足够时 |
| Rank 递减 | 起点 7、入场 1、持平保持、上升重置 | SignalSnapshot | 数据、分析 |
| 选择时钟 | 调仓频率、lag、候选优先级 | SignalSnapshot | 数据、分析；快照时点足够时 |
| EMA 因子 | 15m、EMA7/25、每分钟更新 | AnalysisSnapshot | DatasetSnapshot |
| Rank 形成 | 排序方向、并列规则、Rank 频率 | AnalysisSnapshot | DatasetSnapshot；可能复用因子子产物 |
| universe | 上市时间、历史长度、成交额、缺失率、排除表 | AnalysisSnapshot | DatasetSnapshot |
| 数据 | 新月份、粒度、字段、数据版本 | DatasetSnapshot | 仅复用兼容且覆盖充分的已有数据 |

实现时应把依赖声明编码进 manifest 和配置模型，不能仅靠这张人工维护的表判断复用。

## 5. 快速回放目标

### 5.1 稀疏行情读取

当前执行阶段可能再次扫描全市场 bars。对于候选信号与市场选择完全由 SignalSnapshot
确定的策略，回放只应读取可能成交的候选合约、当前持仓合约及其风险/估值/资金费所需的
时间段和列。需要为每个执行块计算可证明完整的依赖闭包，而不是先读全市场再过滤。

若某种持仓模式、组合风险或动态选择无法证明稀疏输入完整，执行器必须自动使用正确的
全量分块路径，不能为了速度漏读会影响结果的行情。

### 5.2 止盈止损批量扫描

提供研究型 risk sweep，一次载入相同 SignalSnapshot 和稀疏 bars，在严格隔离的状态机中
并行推进多组参数，例如止损集合 × 止盈集合。每组必须拥有独立的账户、持仓、冷却、成本
和事件 ID 状态；不能共享会随参数变化的经济状态。

批量扫描默认只发布：

- 参数组合与完整配置 hash；
- 关键收益、回撤、交易数、胜率和破产/约束状态；
- 输入快照身份、引擎版本、耗时与峰值 RSS；
- 失败或被资源门终止的明确状态。

用户选定组合后再生成单独的正式 ReplayRun、不可变明细和完整报告。不得把 sweep 排名
自动解释为样本外最优，也不得自动替用户选择或发布策略。

## 6. 身份、缓存命中与失效

每层使用规范化配置、父产物 hash、schema/实现版本和必要源码兼容标识计算稳定 identity。
路径名称、显示名称、输出开关和 chunk 大小等非经济字段不得无故破坏经济缓存；但分块恢复
identity 仍须绑定实际计划，避免拼接不兼容 checkpoint。

缓存命中前必须验证：

1. manifest 状态为成功且原子发布完成；
2. 父 ID、父 manifest hash 和所有文件 hash 一致；
3. 时间覆盖、warmup、频率、字段和 Rank 覆盖能力满足请求；
4. schema 与当前读取器兼容，经济实现版本未失效；
5. 快照不存在重复键、时间越界、缺块或截面完整性错误；
6. 正式 run manifest 记录实际命中/未命中的层级及原因。

任何经济逻辑修复都必须显式提升对应实现版本或兼容标识，使旧缓存不会被误用。旧正式 run
继续引用原产物，不因新版本发布而改变。

## 7. 正确性与等价门

第四阶段的首要验收不是“更快”，而是冷启动完整路径与缓存路径的经济结果等价：

- 相同配置、数据和实现下，trades、positions、risk events、costs、equity 及关键指标一致；
- SignalSnapshot 重建与冷启动在线选择产生相同候选信号、时间、reason 和稳定 ID；
- 不同 `chunk_interval`、中断恢复和新进程消费快照时结果一致；
- 边界时间、EMA warmup、合约上市/下市、缺口和资金费时点无前视；
- 篡改、截断、错父级、旧 schema 和字段不足必须在正式产物发布前失败；
- 缓存命中不会改变 R4 当前成交、风险和结束语义。

“一致”的字段和允许差异必须在验收前逐表列出。原则上经济字段要求完全一致；仅运行 ID、
父产物引用、生成时间、耗时和资源诊断等运行元数据可以不同。

## 8. 性能与资源目标

性能验收同时记录冷启动、缓存分析、单组回放和批量扫描，至少包含 wall time、CPU time、
读取行数/字节数、分块数、峰值 RSS 和缓存命中原因。

- 快照生产和回放继续满足当前 `max_process_rss_mib` 硬门。
- 只修改止盈止损时，不得重新计算 universe、EMA 或全市场 Rank。
- 支持稀疏路径的 R4 回放，不得读取与任何候选/持仓依赖无关的全市场行情行。
- N 组 sweep 不得等价于无界地把 N 份整月市场数据或 N 个完整输出表常驻内存。
- 具体加速倍数应在实现前用当前干净基线重新测量后写入阶段验收，不在设计阶段虚构承诺。

当前 R4 月度正式 run 的约 31–35 分钟耗时可作为观察背景，但不能直接作为未来验收基线，
因为源码版本、磁盘缓存和虚拟机资源会影响测量。

## 9. 建议实施与验收阶段

| 阶段 | 目标 | 完成门 | 明确不包含 |
|---|---|---|---|
| A27 | 依赖图、AnalysisSnapshot/SignalSnapshot schema、identity、原子存储和失效规则 | 固定 fixture、hash/篡改/覆盖校验、chunked 生产与恢复 | 稀疏执行和批量扫描 |
| A28 | 从 SignalSnapshot 的确定性 ReplayRun 与稀疏行情读取 | 冷/热逐表经济等价、fallback 完整性、内存门、R4 代表性本地实测 | 多参数 sweep |
| A29 | risk/仓位参数批量扫描与正式组合提升 | 多状态隔离、逐组单跑等价、有界内存、候选转正式 run | 自动选优、分布式集群 |

每阶段开始前仍需用户明确指示；测试、真实回测、联网以及 Git 操作分别按当次授权执行。
实现阶段必须同步对应 `docs/acceptance/Axx.md`、自动验收和持久化上下文。

## 10. 非目标

- 不把回测引擎改成近似估算器，也不从旧 trades 直接推导新止盈止损结果。
- 不修改、覆盖或“升级”既有正式 run artifact。
- 不把 R4 的策略条件写死进通用缓存或执行器。
- 不引入实盘 Client、账户凭据、真实订单或与另一台实盘服务器的运行时耦合。
- 不以全量内存、关闭完整性校验或牺牲最坏情况成交语义换取速度。
- 不在本阶段自动做参数寻优、过拟合判断、样本外验证或策略上线决策。
- 不把全年全市场压力测试设为日常完成门；更大容量测试仍需用户单独授权。

## 11. 第四阶段总体完成定义

只有同时满足以下条件，才能宣布本阶段完成：

1. 用户明确授权并完成 A27–A29，而不是只有本文档；
2. 参数变化可以被机器确定地映射到最早失效层级；
3. R4 的止盈止损/仓位变体可复用既有分析与信号快照完成正式回放；
4. Rank 递减参数变化只重建信号和回放，EMA 参数变化会正确重建分析；
5. 冷启动、缓存回放、分块、恢复及 sweep 单组结果通过经济等价门；
6. 资源、审计、失败关闭、不可变发布和报告重建契约全部保留；
7. 文档、自动验收、正式代表性记录和 Git 状态完成交接。
