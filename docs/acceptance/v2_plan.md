# 第二版分阶段验收计划

本文约束第二版 A12–A18 的协作、测试和提交方式。功能语义以
`docs/design/v2_design.md` 为准，实施边界以
`docs/design/v2_implementation_plan.md` 为准。

## 1. 协作规则

1. 每阶段先实现约定代码、固定样例、验收脚本和对应 `Axx.md`。
2. Codex 在交付验收点时说明测试内容、验证功能、环境搭建、命令、预期结果和代码
   索引。
3. 默认由用户执行测试；未经该阶段明确授权，Codex 不代替用户运行验收。
4. 用户明确许可自行验收后，Codex 才在保留的 `bianbt-acceptance` tmux 会话中按
   文档执行，并如实报告结果。
5. 验收失败只修当前阶段，不混入后续阶段功能。
6. 用户确认或授权的验收通过后，才按用户指示 commit 和 push；“通过”本身不等于
   自动获得 push 授权。
7. 当前阶段未通过，不开始下一阶段。
8. 默认只修改本仓库；访问仓库外部系统或数据前必须解释并获得用户批准。

文档审阅、静态格式检查不算功能验收。联网测试、写 GitHub 和删除数据分别需要用户
在对应任务中授权。

## 3. 标准验收环境

每一阶段的具体命令由对应 `Axx.md` 固定，统一从下列环境开始：

```bash
cd /path/to/bianbt
source .venv/bin/activate
python --version
bianbt --help
```

自动验收脚本位于 `tests/acceptance/`。标准命令形式为：

```bash
pytest -q tests/acceptance/test_acceptance_XX_name.py
```

若阶段需要 CLI 闭环，验收文档必须提供独立 workspace、输入 fixture 和清理范围，
不得读取根目录 `.env`、API key 或实盘数据目录。

## 4. 每阶段共同通过条件

- 验收文档列出的全部自动 item 通过。
- 必要的 CLI 人工步骤输出与文档相符。
- 失败用例在读取大量数据或写正式 run 前失败。
- 产物通过 schema、唯一键、时间范围、run 归属和内容 hash 校验。
- 相同输入复跑具有确定性和幂等性。
- 分块阶段与非分块 reference 的经济列一致。
- 没有读取实盘凭据，没有修改仓库之外的文件。
- 当前阶段相关回归通过，且 V1 兼容门未退化。

只要存在跳过但属于本阶段完成定义的测试，就不能宣称阶段通过。外部网络不可用时，
联网补充测试可以明确标记未执行，但 A18 的真实全链路不能因此被宣布完成。

## 5. 资源和内存验收

A14 以后每份验收记录至少包含：

- 输入合约数、快照数、基础 bar 数和 chunk 大小。
- `lag`、Rank 状态行数、持仓状态数和待成交意图数。
- 理论内存复杂度和实测 peak RSS。
- 配置的软预算/硬上限及超限失败结果。

测试不得通过一次性 collect 全量数据来简化断言。A14 必须证明 lag 1 为 O(N)、固定
L 为 O(N×L)；A16 必须证明风险状态为 O(P)。资源门在写正式成功 manifest 前执行。

## 6. A18 真实数据边界

A18 优先复用已经由用户跑通的教程 DatasetSnapshot，避免重复下载。若需要新的
Binance 公共历史数据，先在 A18 文档列出合约、日期、粒度、预计磁盘和内存，再由
用户决定是否执行联网准备步骤。

代表性真实数据场景至少包括：

1. 当前快照做多 Rank 2、做空 Rank 1。
2. 当前时刻引用上一个调仓快照 Rank 1。
3. 固定保证金重复加仓并命中敞口或可用保证金约束。
4. 基础 K 线内触发止盈/止损，并在报告中追溯到成交。

本机不再以一年全市场为第二版完成门槛。大容量测试等待迁移到更充足的服务器后单独
执行；小型真实测试仍必须通过资源预算，避免再次因无界内存导致服务器宕机。

## 7. 阶段交付模板

Codex 到达每个验收点时应一次性交付：

- 本阶段完成内容和明确未实现内容。
- 用户可以观察到的行为变化。
- 环境准备和完整测试命令。
- 每条测试在验证什么、预期看到什么。
- 相关源代码、fixture、验收脚本和文档路径。
- 已知限制、资源需求和失败后的日志位置。
- 是否存在未执行测试；不得用“应该通过”代替结果。

用户验收后可明确要求：修复、补测、commit/push，或开始下一阶段。
