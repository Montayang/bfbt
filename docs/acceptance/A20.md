# A20：V2 可恢复时间分块执行器验收

A20 将 A18 的经济事件循环改造成真正按时间分块的 V2 worker。目标是证明持仓、资金、
风险和 next-open 事件能够跨块继续，并为后续全市场策略提供不会随回测时长增长的执行
内存边界。

## 1. 本阶段完成内容

- A18 单次循环提取为可注入 `V2ExecutionCheckpoint` 的相同经济内核。
- checkpoint 包含持仓/现金、风险持仓、冷却、待 next-open 意图、稳定序号、上一
  权益、历史峰值、warnings 和累计状态峰值。
- 状态标量写 JSON，状态表写 Parquet，并由 A19 manifest 校验 hash、大小和行数。
- 每个时间块使用独立 `spawn` worker；完成后进程退出，释放 Polars/Python 内存。
- 父进程轮询 worker 的绝对 RSS，超过 `max_process_rss_mib` 时终止当前 worker。
- worker 内继续执行 `max_incremental_rss_mib` 和输入总行数门。
- worker high-water RSS 写入 committed manifest，恢复后仍可生成内存诊断。
- 风险触发可以在块末产生、在下一块开盘成交，事件 ID、成交序号和冷却保持连续。
- `resume` 从最后连续 committed chunk 继续；完整工作区复跑不重新计算经济块。
- 正式 V2 `performance.mode=chunked` 已接入现有分块 factor/Rank 分析和 V2 发布。

## 2. 当前仍未完成

- A20 最终拼接审计表时仍会物化 position instructions、trades、risk events 和 trace。
- V2 artifact 的重复键检查、全局指标和报告生成仍可能物化大表。
- 全市场 24h 动量及 Rank 递减策略尚未实现。
- hard-trigger 同 bar 成交语义尚未实现，当前风险成交仍是 next-bar-open。
- 没有做真实联网、整月或大内存压力测试。

因此 A20 证明“经济执行可分块且可恢复”，还不能宣称整月全市场正式报告已经能在
6 GiB 内完成。A21 负责流式产物/报告，A22–A23 负责实际策略语义。

## 7. 正式配置变化

V2 chunked 必须显式填写：

~~~yaml
performance:
  mode: chunked
  chunk_interval: 6h
  max_input_rows_per_chunk: 5000000
  max_incremental_rss_mib: 2048
  max_process_rss_mib: 5632
  resume_policy: resume
~~~

`chunk_interval` 必须同时是基础 K 线和 risk evaluation interval 的整数倍。整机只有
6 GiB 时建议把绝对门设为 5120，而不是 5632。

## 9. 失败定位

- worker 异常：父进程错误包含 chunk ordinal 和完整子进程 traceback。
- RSS 超限：错误包含 worker PID、实际 RSS 和配置上限；当前块只留 staging。
- checkpoint 错误：检查对应 committed chunk 的 `checkpoint.json` 和 state 文件。
- 经济不等价：验收输出会指出具体表、列和时间点。
- spawn/序列化错误：发生在 chunk 0 前，错误会显示不能序列化的对象类型。
